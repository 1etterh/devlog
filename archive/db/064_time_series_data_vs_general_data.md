## 한 줄 요약

**일반 데이터는 "어떤 대상이 지금 어떤 상태인가"를 저장하고, 시계열 데이터는 "어떤 값이 시간에 따라 어떻게 변했는가"를 저장한다.** 시계열에서는 시간이 데이터의 일부가 아니라 **기본 축(primary axis)**이다.

## 예시로 보기

**일반 데이터** — 장비 테이블

| id | hostname | ip | status |
|---|---|---|---|
| 1 | sw-core-01 | 10.0.0.1 | UP |

→ 상태가 바뀌면 같은 행을 **UPDATE**. 과거 상태는 사라진다.

**시계열 데이터** — CPU 사용률

| timestamp | metric | labels | value |
|---|---|---|---|
| 15:00:00 | cpu_usage | host=sw-core-01 | 23.1 |
| 15:00:15 | cpu_usage | host=sw-core-01 | 25.4 |
| 15:00:30 | cpu_usage | host=sw-core-01 | 61.0 |

→ 값이 바뀌면 **새 행을 INSERT**. 과거는 절대 덮어쓰지 않는다.

## 핵심 차이 비교

| 구분 | 일반 데이터 (OLTP/RDB) | 시계열 데이터 (TSDB) |
|---|---|---|
| 데이터 단위 | 엔티티(행) | (시간, 값) 쌍의 연속 = 시리즈 |
| 쓰기 패턴 | INSERT/UPDATE/DELETE 혼합 | **거의 append-only** (끝에 추가만) |
| 수정 | 자주 발생 | 거의 없음 (과거는 불변) |
| 쓰기량 | 상대적으로 적음 | 매우 많음 (장비 수 × 지표 수 × 수집 주기) |
| 조회 패턴 | 특정 행 1건, 조인 | **시간 범위** + 집계 (avg, rate, max over 5m) |
| 개별 값의 가치 | 한 건 한 건이 중요 | 개별 점보다 **추세·패턴**이 중요 |
| 보존 정책 | 대개 영구 보관 | 오래된 건 **다운샘플링 후 삭제** (retention) |
| 인덱스 기준 | PK, 비즈니스 키 | 시간 + 라벨(태그) |
| 압축 | 일반적 | 매우 높음 (delta-of-delta, XOR 등으로 인접 값 차이만 저장) |
| 대표 저장소 | MySQL, PostgreSQL | Prometheus, InfluxDB, TimescaleDB, VictoriaMetrics |

## 후속 질문: 시계열 DB는 row 형태가 아니라 다른 형태로 저장하나?

맞다. 앞의 표는 논리적으로 보여주기 위한 형태일 뿐이고, 대부분의 TSDB는 실제로 "시간 1개 = 행 1개"로 저장하지 않는다. **시리즈별로 값을 묶어 연속 저장**한다.

**RDB (row 저장)** — 한 행이 디스크에 붙어 있음

```
[15:00:00 | cpu | host=A | 23.1] [15:00:00 | cpu | host=B | 40.2] [15:00:15 | cpu | host=A | 25.4] ...
```
→ 매 행마다 metric 이름·라벨이 반복되고, 같은 시리즈의 값이 흩어져 있음

**TSDB (시리즈 단위 저장)** — 시리즈 하나의 값끼리 모음

```
series#1 = cpu{host=A}
  timestamps: [15:00:00, 15:00:15, 15:00:30, ...]
  values:     [23.1,     25.4,     61.0,     ...]
```
→ 라벨은 한 번만 저장하고 ID로 참조, 같은 시리즈 값이 붙어 있어 범위 조회는 연속 읽기가 되고 압축률도 높음
