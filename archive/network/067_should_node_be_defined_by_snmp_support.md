아니요, 노드를 "SNMP를 지원하는 OS를 가진 장비"로 정의하는 건 피하는 게 좋습니다. SNMP는 노드가 **무엇인가**가 아니라 노드의 정보를 **어떻게 가져오는가**에 해당하기 때문입니다. 정의에 수집 방법을 넣으면 다음 문제가 생깁니다.

**1. 노드인데 SNMP로 읽지 못하는 장비가 많습니다**

| 경우 | 예 | 실제 수집 방법 |
|---|---|---|
| 서버 | Linux는 snmpd가 기본으로 깔려 있지 않고, Windows SNMP 서비스는 지원 중단된 선택 기능 | 에이전트, Docker API |
| SNMP를 꺼 두거나 막은 네트워크 장비 | 보안 정책, 방화벽, v3 계정을 모름 | SSH CLI, NETCONF, 수동 등록 |
| 사람이 등록한 장비 | CSV 가져오기, CMDB 연동 | 가져오기 |

노드 설계의 유형에는 "서버"가 있고, 서버는 보통 SNMP가 아니라 에이전트로 수집합니다. 정의에 SNMP를 넣으면 이 설계와 어긋납니다.

**2. 설정이 바뀌면 노드 여부가 바뀝니다**
- 정의가 "SNMP를 켠 장비"라면, 누가 SNMP를 끄거나 계정이 틀렸을 때 그 장비는 노드가 아니게 됩니다. 그러면 링크와 서비스가 가리키던 대상도 사라집니다.
- 노드 설계에는 `status`의 "수집 실패(UNKNOWN)", 즉 "장비는 있는데 못 읽는 상태"가 있습니다. 이 상태가 있으려면 노드 정의가 수집 성공 여부와 따로 있어야 합니다.

**3. "지원한다"는 조건은 거의 모든 장비를 걸러내지 못합니다**
- Linux라면 어디든 snmpd를 깔 수 있습니다. 그래서 "지원하는 OS"로 정하면 사실상 모든 장비가 들어옵니다.
- 장비를 실제로 구분하는 건 "SNMP가 켜져 있는가"인데, 이건 위 2번의 설정 상태 문제입니다.

**일반 정의가 이미 맞는 형태입니다**

> 자기 OS와 **관리 주소**를 가진 장비 1대

- "관리 주소"는 NMS가 접속해 정보를 읽는 주소이고, 특정 프로토콜에 묶여 있지 않습니다. SNMP든 SSH든 에이전트든 됩니다. "SNMP 지원 장비"라는 생각은 이 조건에 이미 들어 있는 셈입니다.
- 다만 관리 주소의 출처로 RFC 3411을 달고 "관리 대상은 SNMP 엔티티를 가진 노드"라고 적으면 SNMP가 정의 조건처럼 읽힐 수 있습니다. RFC 3411은 SNMP가 무엇을 관리하는지 정한 문서이지, 토폴로지 노드를 정의한 문서가 아닙니다.

**SNMP가 들어갈 자리**

| 넣고 싶은 것 | 위치 | 예 |
|---|---|---|
| 노드를 어떤 방법으로 수집하나 | 노드 속성(설계) | `collectMethod`: SNMP v2c / SNMP v3 / 에이전트 / 없음 |
| 1차로 지원할 범위 | 프로젝트 범위 결정(설계) | "1단계는 SNMP로 수집할 수 있는 네트워크 장비만" |
| 노드의 정의 | 일반 지식 | 지금처럼 OS + 관리 주소, 수집 방법과 무관하게 |

"1단계는 SNMP 장비만 다룬다"는 **범위**로는 충분히 정할 수 있습니다. 다만 그건 정의가 아니라 설계 문서에 둘 결정입니다.
