## 의문

NMS에서 node, interface, link는 수집 방식(자동·수동)에 따라 정해질 뿐이고, 그래프를 바꾼다고 실제 네트워크가 바뀌지는 않는다. 그래서 편집 기능은 배치, 프레임, 표시 여부, 색상 위주가 될 것이다. 이런 경우 ECharts와 xyflow/vue 중 무엇을 추천하는가?

## 답변

그 전제라면 이 화면은 "토폴로지 편집"이 아니라 **"수집된 네트워크 위에 씌우는 화면 배치(뷰) 편집"**이다. 이렇게 보면 xyflow의 큰 장점 중 하나인 연결선 만들기·핸들·연결 검증은 거의 쓸 일이 없다. 그래서 엔진은 **프레임 요구가 얼마나 복잡하냐**로 정하면 된다.

### 추천

| 프레임 요구 수준 | 추천 |
|---|---|
| 겹치지 않는 사각형 배경 정도. 노드를 끌어도 프레임은 그대로 | **ECharts 하나로 유지** |
| 프레임 크기 조절, 프레임을 끌면 안의 노드도 같이 이동, 노드를 끌어 넣고 빼면 소속이 바뀜, 중첩 프레임 | **편집 = xyflow, 보기 = ECharts** |

"프레임"이라는 이름을 붙이면 보통 두 번째 수준을 기대하게 되니, **편집 = xyflow, 보기 = ECharts**를 권한다.

### 근거: 기능별 비교

| 편집 기능 | ECharts (graph series) | xyflow/vue |
|---|---|---|
| 배치 (드래그, 좌표 저장) | `layout: 'none'` + draggable로 가능 | 기본 제공 |
| 여러 개 선택해서 함께 이동, 격자 맞춤 | 직접 구현 | 기본 제공 (selection, `snapGrid`) |
| **프레임** | 그룹 개념이 없음. `graphic` 사각형을 덮어 그리고, 줌·이동할 때마다 좌표를 맞추고, 소속 판정을 직접 해야 함 | parent node, `extent: 'parent'`, `NodeResizer` 기본 제공 |
| 표시 여부 | 데이터에서 빼거나 style로 숨김 | `hidden` 속성 |
| 색상 | itemStyle | 노드 컴포넌트의 style |
| 노드 수가 많을 때 (수백~수천 개, 실시간 상태 반영) | canvas라서 빠름 | DOM 방식이라 1천 개 안팎부터 느려짐 |

표시 여부와 색상은 어느 엔진으로든 쉽다. 차이가 나는 건 **프레임과 여러 개 선택 편집**인데, ECharts에서는 이 부분이 거의 다 직접 짜야 하는 코드가 된다. 같은 기능 범위로 두 엔진을 각각 구현해 비교했을 때도 주석을 뺀 코드가 xyflow 384줄, ECharts 613줄이었고, 프레임을 넣으면 차이가 더 벌어질 것이다. 반대로 대시보드는 장비가 많고 상태가 계속 바뀌니 ECharts가 맞다.

### 엔진보다 먼저 정할 것: 데이터 분리

전제를 그대로 데이터 모델로 옮기면 된다.

- **네트워크 데이터** (수집, 읽기 전용): node, interface, link
- **뷰 데이터** (사용자가 편집): `{ nodeId → x, y, hidden, color }`, `frames[{ id, rect, parentId, label, color }]`

두 엔진은 이 뷰 데이터를 읽고 쓰는 각자의 어댑터일 뿐이라고 보면, 편집과 보기를 다른 엔진으로 나눠도 다음 문제만 신경 쓰면 된다.

- 두 화면의 모양 차이 (노드 모양, 라벨 위치)
- 좌표계를 맞추는 일 (xyflow는 노드 왼쪽 위 기준, ECharts는 중심 기준이라 변환 필요)

뷰 데이터에는 "수집 데이터에 없는 노드가 생기거나 사라진 경우"를 처리하는 규칙도 필요하다. 새 노드는 자동 배치하고, 사라진 노드의 위치 정보는 버리는 식이다.

남은 결정은 프레임을 어느 수준으로 만들지다. 프레임 크기 조절이나 끌어서 소속 바꾸기가 필요 없다면 ECharts 하나로 가는 게 가장 싸다.
