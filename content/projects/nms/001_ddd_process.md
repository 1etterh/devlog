## 배경

장비·포트·링크·사이트를 지도와 토폴로지 맵으로 보여 주는 NMS(Network Management System)를 만들고 있다. 설계에 DDD(Domain-Driven Design)를 적용하려고 했다.

## 보통의 순서

DDD를 시작할 때 흔히 권하는 순서는 이렇다.

1. **이벤트 스토밍**: 업무에서 일어나는 일을 과거형 이벤트("장비가 발견됨")로 펼친다. 템플릿: [[dev/ddd/event-storming-template.canvas|이벤트 스토밍 템플릿]]
2. 이벤트 묶음에서 경계(바운디드 컨텍스트)와 애그리거트를 찾는다.
3. 그다음에 데이터 모델을 정한다.

이벤트 스토밍을 먼저 하라는 이유는, 업무 규칙이 사람들 머릿속에만 있고 문서가 없을 때 그걸 끌어내는 도구이기 때문이다.

## 이 프로젝트의 예외: 도메인 정의를 먼저

이벤트 스토밍을 먼저 해 보려 했는데 감이 잡히지 않았다. 그래서 순서를 바꿨다.

| | 일반적인 업무 도메인 | NMS |
|---|---|---|
| 다루는 대상 | 회사마다 다르고 문서가 없다 | 장비·포트·링크가 **표준**(RFC 8345, SNMP MIB)으로 이미 정의돼 있다 |
| 참고할 것 | 현업 담당자의 머릿속 | 표준 문서, 일반 NMS 제품 |
| 먼저 할 일 | 이벤트로 규칙 끌어내기 | **무엇이 있는가**(데이터)부터 정리 |

대상이 표준으로 정해진 도메인에서는 "무엇이 있는가"를 먼저 잡는 게 자연스러웠다.

## 진행한 과정

1. **일반 지식 정리**: 표준과 일반 NMS 기준으로 사이트·노드·인터페이스·링크·서비스를 정리했다 → [[cs/network/nms/index|NMS 토폴로지 데이터]]
2. **일반 지식과 프로젝트 결정 분리**: "우리 모델은…" 같은 문장, 자체 정의 값, 화면 용도, DB 안을 일반 지식 문서에서 빼서 설계 문서로 옮겼다. 섞여 있으면 어디까지가 표준이고 어디부터가 내 결정인지 흐려진다.
3. **속성 표 작성**: 필드마다 설명 · 등록경로 · **수정**(고정 / 수정 가능 / 자동 갱신)을 적었다.
4. **수정 열 → 이벤트 후보**: 값이 바뀌는 필드가 곧 이벤트다.

| 수정 | 이벤트 스토밍에서 | 예 |
|---|---|---|
| 고정 | 생성 이벤트에서 한 번만 정해짐 | 장비 발견됨, 장비 등록됨 |
| 수정 가능 | 사람의 **명령** → 이벤트 | 장비 승인됨, 사이트 지정됨, 사이트 이전됨 |
| 자동 갱신 | 시스템·**정책**이 일으키는 이벤트 | 상태 변경됨, 수집 실패함 |

5. **이벤트 스토밍** (진행 중): 4의 후보를 펼치고, 각 이벤트 뒤에 "그래서 무엇이 이어지나"를 붙인다. 예: 장비 승인됨 → 주기 수집 시작 → 맵에 표시. 여기서 아직 정하지 않은 규칙이 드러난다.

## 주의할 점

- 데이터 정의만 하고 끝내면 **언제·누가·왜 바뀌는가**가 빠진다. 예: `approval = pending / approved / ignored`는 정했지만, 무시한 장비가 다시 발견되면 어떻게 할지는 이벤트를 펼쳐 봐야 보인다.
- 그래서 순서를 바꿨더라도 이벤트 스토밍은 건너뛰지 않고 **이어서** 한다.
