## "포트"가 가리키는 것

한국어로는 모두 "포트"라고 부르지만 계층이 다른 세 가지가 섞여 있다. 앞의 둘은 장비의 **인터페이스**이고, 마지막은 TCP/UDP의 **번호**다.

| 구분 | 계층 | 예 | 무엇인가 |
|---|---|---|---|
| 물리 포트 | L1~L2 | 스위치 `Gi1/0/1`, 서버 NIC `eth0` | 케이블이 꽂히는 실제 구멍 |
| 논리 포트 | L2~L3 | `Vlan10`(SVI), `Port-channel1`(LAG), `docker0`, `veth…` | 소프트웨어로 만든 인터페이스. 케이블이 없다 |
| 포트 번호 | L4 | `5432/tcp`, `8080/tcp` | 한 IP 안에서 프로세스를 구분하는 번호 |

계층 번호는 [[cs/network/001_osi_layers|OSI 7계층과 TCP/IP 4계층]] 참고.

## Docker `-p A:B`의 A와 B는 어느 포트인가?

둘 다 **포트 번호(L4)** 다. 인터페이스가 아니다.

```bash
docker run -p 15432:5432 postgres
```

| | 이름 | 뜻 |
|---|---|---|
| A (`15432`) | 호스트 포트 | 호스트(서버)의 IP에 열리는 포트. 밖에서 들어오는 입구 |
| B (`5432`) | 컨테이너 포트 | 컨테이너 안에서 서비스가 실제로 listen하는 포트 |

Docker는 iptables 규칙(DNAT)으로 `호스트IP:A`로 들어온 요청을 `컨테이너IP:B`로 넘긴다. 이 과정에서 물리 포트(`eth0`)와 논리 포트(`docker0`, `veth`)를 지나가지만, `-p`가 지정하는 건 그 위의 번호뿐이다.

- 인터페이스와 이어지는 건 IP를 통해서다. `-p 10.0.0.5:15432:5432`처럼 앞에 IP를 붙이면 그 IP를 가진 인터페이스로 들어온 요청만 받는다. 생략하면 모든 IP(`0.0.0.0`)에 열린다.
- Docker API(`docker inspect`)에서는 `NetworkSettings.Ports`에 둘이 함께 나온다.

```json
"Ports": { "5432/tcp": [ { "HostIp": "0.0.0.0", "HostPort": "15432" } ] }
```

## 누가 부르느냐에 따라 쓰는 번호가 다르다

| 호출하는 쪽 | 주소 |
|---|---|
| 다른 서버 | `호스트IP:15432` (A) |
| 같은 Docker 네트워크의 다른 컨테이너 | `컨테이너이름:5432` (B) |

그래서 서비스의 포트를 기록할 때 하나만 적으면 어느 쪽인지 모호하다. 호스트 포트와 컨테이너 포트를 나눠 적는다. 서비스를 토폴로지 데이터로 다루는 예는 [[cs/network/nms/data/topology/service|서비스(Service)]] 참고.

## 요청이 포트를 따라 이동하는 과정

### 프로토콜과 포트

"HTTP 포트"가 따로 있는 게 아니다. 서비스가 **listen하는 포트**가 있고, "HTTP = 80"은 보통 이 번호를 쓰자는 관례(well-known port)다.

| 프로토콜 | 계층 | 포트와의 관계 |
|---|---|---|
| TCP, UDP | L4 | 포트 번호를 **가진** 프로토콜. TCP 5432와 UDP 5432는 서로 다른 포트 |
| HTTP, SSH, PostgreSQL | L7 | TCP 위에서 돈다. 관례상 HTTP 80, HTTPS 443, SSH 22, PostgreSQL 5432 |
| DNS | L7 | 주로 UDP 53 (응답이 크면 TCP 53) |

- `http://example.com`은 `example.com:80`의 줄임이다. 서버가 8080에서 listen하면 `:8080`을 적어야 한다.
- 연결 하나는 **출발 IP:포트 → 도착 IP:포트**(+ TCP/UDP)로 구분한다. 요청하는 쪽은 OS가 고른 **임시 포트**(ephemeral port, Linux 기본 32768~60999)를 쓴다.

### 예시 1: 브라우저 → nginx → 컨테이너 (HTTP over TCP)

서버 `10.0.0.5`에 nginx가 80에서 listen하고, 앱은 `docker run -p 8080:3000`으로 떠 있다.

| 단계 | 출발 | 도착 | 받는 쪽 |
|---|---|---|---|
| ① 브라우저가 `http://10.0.0.5` 요청 | `192.168.0.3:51234` (임시 포트) | `10.0.0.5:80` | nginx |
| ② nginx가 앱으로 전달(reverse proxy) | `10.0.0.5:41022` (임시 포트) | `127.0.0.1:8080` | Docker 포트 포워딩(호스트 포트) |
| ③ Docker가 컨테이너로 넘김(DNAT) | 같은 연결 | `172.17.0.2:3000` | 앱 프로세스(컨테이너 포트) |
| ④ 응답 | 거꾸로 같은 길 | `192.168.0.3:51234` | 브라우저 |

서비스 포트는 nginx의 80과 앱의 3000(호스트에서는 8080)이다. 51234, 41022 같은 임시 포트는 연결마다 바뀐다.

### 예시 2: 앱 → DB (PostgreSQL over TCP)

| 호출 위치 | 출발 | 도착 |
|---|---|---|
| 같은 Docker 네트워크의 앱 컨테이너 | `172.17.0.2:39876` | `db:5432` (컨테이너 포트) |
| 다른 서버의 앱 (`-p 15432:5432`) | `10.0.0.7:44120` | `10.0.0.5:15432` (호스트 포트) → 컨테이너 `5432` |

### 예시 3: DNS 조회 (UDP)

| 단계 | 출발 | 도착 |
|---|---|---|
| 질의 | `192.168.0.3:53001/udp` | `8.8.8.8:53/udp` |
| 응답 | `8.8.8.8:53/udp` | `192.168.0.3:53001/udp` |

UDP는 연결 수립(3-way handshake) 없이 질의 하나, 응답 하나로 끝난다. 포트로 프로세스를 구분하는 방식은 TCP와 같다.

### 정리

- 기록할 것은 **listen 포트**(80, 3000, 5432)와 프로토콜(TCP/UDP)이다.
- 임시 포트는 기록하지 않는다. 연결을 관찰해 "누가 누구를 부르나"를 알아낼 때, **listen 포트 쪽이 호출 대상**이라는 판단 근거로 쓴다.

## 패킷은 NIC에서 프로세스까지 어떻게 가나?

패킷을 받는 카드는 **NIC**(Network Interface Card)다. NAC은 보통 Network Access Control(802.1X 등으로 단말의 망 접속을 허용·차단하는 보안 기능)을 뜻해 다른 것이다.

NIC로는 **물리 포트**(`eth0`)로 들어온다. NIC는 **포트 번호를 모른다.** 포트 번호를 보고 프로세스를 고르는 건 OS 커널이다.

| 단계 | 누가 | 보는 것 | 하는 일 |
|---|---|---|---|
| ① 케이블 → 물리 포트 | NIC | 전기·광 신호 (L1) | 비트를 프레임으로 복원 |
| ② 프레임 필터 | NIC | 목적지 **MAC** (L2) | 내 MAC·브로드캐스트·멀티캐스트만 받고 나머지는 버림 (promiscuous 모드면 다 받음) |
| ③ 메모리로 | NIC → RAM | — | DMA로 메모리에 복사, 인터럽트로 CPU에 알림 |
| ④ IP 처리 | 커널 | 목적지 **IP** (L3) | 내 IP면 위로, 아니면 포워딩·버림. Docker의 DNAT(`호스트IP:A` → `컨테이너IP:B`)가 여기서 일어남 |
| ⑤ 소켓 찾기 | 커널 | 목적지 **포트 번호** + TCP/UDP (L4) | 그 포트에서 listen 중인 소켓을 찾음. 없으면 TCP는 RST, UDP는 ICMP port unreachable |
| ⑥ 프로세스 | 앱 | 데이터 (L7) | `recv()`로 읽음 (HTTP 파싱 등) |

계층마다 보는 주소가 다르다.

| 주소 | 질문 | 보는 쪽 |
|---|---|---|
| 물리 포트 (`eth0`) | 어디로 들어왔나 | NIC |
| MAC | 이 카드 앞이 맞나 | NIC |
| IP | 이 장비 앞이 맞나 | 커널 |
| 포트 번호 | 이 장비의 어느 프로세스인가 | 커널 |

Docker 컨테이너라면 물리 포트(`eth0`) → 논리 포트(`docker0` → `veth`) → 포트 번호로 프로세스를 찾아간다. 세 가지 포트를 차례로 지나는 셈이다.

**예외**: 요즘 NIC는 성능을 위해 L3·L4 헤더를 일부 본다. 그래도 프로세스를 정하는 건 커널이다.

- RSS(Receive Side Scaling): IP·포트로 해시를 만들어 패킷을 여러 CPU 큐로 나눈다.
- 체크섬 오프로드: TCP/UDP 체크섬을 NIC가 대신 계산한다.
- SmartNIC / DPU: 방화벽·로드밸런싱까지 카드에서 처리한다(예외적인 경우).
