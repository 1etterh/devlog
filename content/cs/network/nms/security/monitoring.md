[[cs/network/nms/data/monitoring/index|감시]] 데이터(측정값·이벤트·경보)를 다룰 때의 주의점.

## 로그 속 민감정보

syslog·trap 문장에는 생각보다 많은 정보가 섞인다.

| 섞이는 정보 | 예 |
|---|---|
| 사용자 계정 | 로그인 성공·실패 로그의 사용자 이름 |
| 개인을 가리키는 값 | 단말 IP·MAC(사람과 연결되면 개인정보) |
| 비밀번호 조각 | 로그인 실패 때 사용자 이름 칸에 비밀번호를 잘못 입력한 기록 |
| 설정 내용 | 설정 변경 로그에 community·키가 그대로 찍히는 장비 |

대응:

- 수집 단계에서 알려진 패턴(community, 키)을 **마스킹**한다.
- 원문 로그 조회는 권한을 따로 둔다. 경보·요약만 보는 사용자와 나눈다.
- **보관 기간**을 정한다. 법·사내 규정(접속 기록 보관 의무 등)과 저장 비용 사이에서 정하고, 지나면 지운다([[cs/network/nms/data/resolution|데이터 해상도]]).

## 경보 폭주

trap·syslog는 장비가 보내는 대로 받으므로 NMS가 감당 못할 양이 올 수 있다.

| 원인 | 결과 |
|---|---|
| 포트가 계속 up/down 반복(flapping) | 초당 수백 건 이벤트 |
| 코어 장애로 아래 장비 전부 경보 | 진짜 원인이 묻힌다 |
| 위조 trap 대량 전송 | NMS 마비, 저장소 가득 참 |

대응:

- 장비·종류별 **초당 수신 제한**, 넘으면 버리고 "폭주 중" 경보 하나로 묶는다.
- 같은 대상·종류는 경보 1개로 갱신한다([[cs/network/nms/data/monitoring/event#경보alarm|경보]]).
- 토폴로지로 아래쪽 경보를 묶는다(근본 원인 분석). 감시가 마비되면 장애를 못 보므로 NMS 자체의 가용성도 보안 문제다.

## 감시의 공백

공격자는 감시를 끄는 것부터 한다.

- **수집 실패를 장애와 구분해 알린다.** 장비가 SNMP를 막거나 trap 대상을 바꾸면 "조용한" 상태가 된다. 오래 안 들어오는 것도 경보다.
- 경보 규칙·임계값 변경, 장비 무시(ignore) 처리는 이력을 남긴다. 감시를 끄는 가장 쉬운 길이다.
- 장비 시계가 틀리면 사고 조사 때 이벤트 순서가 뒤섞인다. NTP로 시간을 맞추고 장비 시각과 받은 시각을 같이 저장한다.

## NMS 자신

NMS 서버도 감시 대상이다.

- NMS 서버의 접속·설정 변경·인증 정보 조회를 기록한다.
- NMS 계정에 다중 인증(MFA)을 건다. NMS 관리자 계정은 망 전체 관리자와 같다.
- NMS와 감시 데이터 저장소(DB)는 관리망 안에 두고, 사용자는 웹 화면으로만 접근한다.
